# 費用削減4項目の実装・ローカル検証

後続の本番反映記録は [cost-reduction-production-release-2026-09-13.md](cost-reduction-production-release-2026-09-13.md) を参照。以下はローカル検証時点の記録。

実装対象は、ボット向けrobots、ジャンル詳細の表示用集約、販売履歴の年次保存への統一、発売日初日の販売数確定。通常日の再実行に対する新しい計算・基準復元・収集ロックは追加していない。

本番デプロイ、本番設定の更新、本番データの補正・削除は実施していない。実請求額と本番全件の移行完了は、このローカル検証では判定しない。

## 実装

### ボット

`web/app/robots.ts`にMeta-ExternalAgentとAmazonbot向けの`Disallow: /`を追加。従来のワイルドカード向けAllow、`/api/`・`/search`のDisallow、サイトマップは維持。検索エンジンやSNSプレビュー用UAを追加で拒否していない。

robotsに従う巡回への対策であり、UAを偽装するアクセスやrobotsを無視するアクセスの強制遮断ではない。有料WAF等は導入していない。

### ジャンル詳細

- `functions/src/batch/genreDetailView.ts`で、1ブロック最大300件の表示用データを生成。圧縮後256KiB、展開後4MiB以下に分割し、チェックサム・件数・ブロック位置を保存する。
- `rebuildSiteStats.ts`が既に読んだ商品配列を再利用する。ジャンルごとの全商品再読込や、一覧描画時の商品IDからの個別読込は追加していない。
- `web/lib/firebase/genreDetailView.ts`から候補を取得し、既存の公開判定、TL/BL・作品形式の絞り込み、offset・表示件数をそのまま通す。候補数の従来上限も維持する。
- `salesCount`の同値時はFirestoreの降順クエリと同じ実ドキュメントID順。未設定フィールドとnullを区別し、カードに必要な値を保持する。
- 商品を更新する収集、表示制御、補正経路は、更新開始前に共有の更新番号を進める。更新中の集約参照は禁止。商品配列の取得開始時点で別の更新処理が動いていた場合も公開しない。
- 新しい版を全て保存した後、更新番号と更新中フラグをトランザクションで確認して公開する。同一処理内で集約する場合は、商品更新が終わってから公開する。
- Webは毎回、更新番号をFirestoreから確認する。新規のブロック読込を挟んだ場合は読込後も再確認する。キャッシュだけで取り出せる不変データは最初の確認時点の状態として返す。
- キャッシュはサイズ換算16MiB・128エントリを上限とし、ルート情報は60秒で期限切れ。24時間以上経過した非現行版を整理し、現在も公開し得る生成中の版は削除しない。
- 欠損・破損・更新競合時は従来クエリに戻る。集約生成の失敗で、既存の検索・ランキング等の生成処理を停止させない。
- `GENRE_DETAIL_AGGREGATION_ENABLED=true`で生成、`GENRE_DETAIL_READ_MODE=prefer`で利用。未設定時は生成無効・従来読込。更新開始前の無効化処理は、生成フラグによらず動作する。

### 年次履歴のみの保存

既存の`METRIC_HISTORY_WRITE_MODE=year`を使い、ローカルで二重書き込みが終了することを検証した。商品本体の現在値更新は継続する。`dailyMetrics`の既存データは削除・更新しない。

年次の販売数・価格・日次差分の保存項目に、初日確定の根拠・観測時刻・定義バージョンを追加した。Functions/Webの型、年次への変換、比較・移行スクリプトも対応。評価・レビュー数等は、ユーザーの確認どおり商品本体の現在値だけを保持する。

既存のlegacy/year/dualモードは維持。商品本体とその履歴は、保存前に必要な更新を構築し、同じコミットに収まるように確保する。年次の構築エラーやコミット失敗で商品本体だけが残るケースも検証した。

### 初日の販売数

発売日D、論理バッチ日D+1、実際の商品観測日がJSTのD+1、履歴キーがDで一致するとき、Dの日別本数をその観測時の累計本数で確定する。

| 観測日 | 累計 | 履歴キー | 日別本数 |
|---|---:|---|---:|
| 9/1 | 50 | 9/1 | 未確定 |
| 9/2 | 120 | 9/1 | 120 |
| 9/3 | 200 | 9/2 | 80 |
| 9/4 | 260 | 9/3 | 60 |

商品本体の`releaseDaySales`に確定値・当時価格・観測時刻を保持し、日次順位の基準日が進んだ後も初日のグラフを表示する。週間・月間・累計へ120を再加算しない。

前日発売の登録済み作品を狭い発売日範囲クエリで追加対象にし、既存対象と重複排除する。取得済みの商品情報を既存値として再利用する。TL/BLの別ジョブでも追加対象を分類する。分類情報も取得元URLも不明な作品は強引に分類せずログに記録する。

0本は有効。欠損・負値・発売日の矛盾・日付をまたいだ不適切な観測では初日を確定しない。発売翌日を取り逃した場合、後日の累計を初日へ流用せず、初日の仮スナップショットからの複数日差分を通常1日分として表示しない。

旧作品収集処理が、priority方式の商品に対して別の日付基準の差分を上書きしないよう保護する。確定済み初日の点も別経路で保護する。

過去補完ツール`functions/src/tools/backfillReleaseDaySales.ts`は、明示した最大50商品だけを対象にする。年次にD+1の点固有の取得時刻・累計・価格が残っている場合だけ補正案を出す。実行には対象プロジェクトの明示が必要で、現在の累計・通常日の基準は巻き戻さない。今回の適用はdemoプロジェクトの検証用商品だけ。

## 再検証

別のPowerShellで、リポジトリ直下から専用エミュレータを起動する。Javaとjarは環境に合わせて指定する。日本語ロケールでエミュレータのルール読込が失敗したため、Javaの表示言語を英語に指定した。

```powershell
java '-Duser.language=en' '-Duser.country=US' -jar "$env:USERPROFILE/.cache/firebase/emulators/cloud-firestore-emulator-v1.22.0.jar" --host 127.0.0.1 --port 8188 --project_id demo-cost-review --rules firestore.rules --single_project_mode --single_project_mode_error
./scripts/test-cost-reduction-local.ps1
```

HTTP比較は、同じWeb本番ビルドを3155（`GENRE_DETAIL_READ_MODE=prefer`）と3156（`legacy`）で起動し、`node web/tests/costReductionHttp.compare.mjs`を実行する。両方とも上記の専用エミュレータを指定する。

## 本番反映時の順序と費用確認

1. 新しい発売日クエリの複合インデックス、集約payload等の索引除外を先に反映する。
2. 先にWebの初日表示対応を反映し、ジャンル読込はlegacyを維持する。その後、収集・表示制御・補正の全更新経路へ無効化処理と初日確定を反映する。履歴の比較期間は書込dual・読込yearとし、実環境の設定を明示して適用する。
3. 初日確定を確認し、集約生成ジョブに`GENRE_DETAIL_AGGREGATION_ENABLED=true`を設定する。既存の索引再生成で専用集約を生成し、本番データの表示互換と生成負荷を照合する。
4. ジャンル側が合格後、Webへ`GENRE_DETAIL_READ_MODE=prefer`を設定する。戻す場合は`legacy`。
5. 販売履歴は日次収集が停止している時間帯に移行スクリプトで全件比較し、欠落・不一致・余剰が0であることを確認した後、収集ジョブとFunctionsの実環境を`METRIC_HISTORY_WRITE_MODE=year`、読込側を`METRIC_HISTORY_READ_MODE=year`へ統一する。少数作品の一致だけでは切り替えない。照合から切替までの間にも履歴を更新しない。
6. 二重書き込み終了後に読込をlegacyへ戻す場合は、停止期間の履歴補完が必要。過去dailyMetricsを残すことだけでは即時の完全ロールバックにはならない。

生成には追加Write、更新番号のRead/Write、前日発売候補のReadと追加取得時間が発生する。今回の2ジャンル・6ブロックの例では、1回の公開に11 Write（整理・制御分を除く）。候補検索はTL/BLの各ジョブで実行される。総費用は画面Readの減少とこれらの増分を合わせ、同じ利用量で比較する。請求減額そのものは本番反映後に確認する。

生成ログの`published`・`revision`・`genreCount`・`blockCount`・`writeCount`と、制御ドキュメントの更新番号、Webの失敗ログを監視する。プロセス強制終了で更新中トークンが残った場合は従来読込を続ける。該当実行（トークン内のexecution・startedAt）と他の商品更新が停止していることを確認し、残ったトークンだけを削除して索引を再生成する。時刻経過だけでは解除しない。
