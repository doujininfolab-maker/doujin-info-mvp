# 費用削減3案の影響・デグレ再評価

確認日: 2026-09-12。対象はジャンル詳細のcompact索引利用、Meta-ExternalAgent／Amazonbotの個別巡回抑制、フッター6リンクの先読み停止。

ローカルの現行ソース、前回保存した本番調査結果、公式仕様を照合した。本番は `doujin-info-prod`（272801294765）、Webはasia-east1、日次ジョブはasia-northeast1。今回、本番への追加データ走査・設定変更・デプロイは行っていない。追加したのは本書とローカル診断用ファイルのみ。既存の `web/tsconfig.tsbuildinfo` 等の変更は触っていない。

## 判断

ユーザーの追加条件（機能維持、性能維持、Read削減、総課金削減、大きなデメリットなし、デグレなし、一定のボット対策）を採用基準とする。3案をそのまま実施して全条件を満たせるとは、現段階では判定できない。

robots.txtは検索・共有用の別エージェントを維持した個別設定に限定して最初の検証候補にする。フッターは遷移速度が維持できると確認できた場合のみ採用する。ジャンル詳細は単純置換に実際の互換性問題があり、前案の「getCatalogProductsPage等をそのまま再利用できる」は修正する。さらに、分類・順序を合わせるだけでは日次索引の反映遅延を解消できないため、日次compactだけの候補選択は今回の機能維持条件では採用しない。

| 案 | 機能へのリスク | 主なデメリット | 判定 |
|---|---|---|---|
| フッター6リンクにprefetch=false | 低 | 初回クリック時の待ち時間が増える可能性 | 性能維持が未確認のため採用保留 |
| Meta-ExternalAgent／Amazonbotの個別Disallow | アプリ動作は低、集客は不確定 | 対象サービスによる情報利用・発見機会が減る可能性。守らない巡回には効かない | 独立した変更として最初に検証する候補 |
| ジャンル詳細をcompact索引中心に変更 | 単純置換では高 | 更新反映の遅れ、表示条件・順位・ページ送りの変化。CPU・メモリ負荷増の可能性 | 現案は不採用。更新反映も維持できる別設計が必要 |

「影響がない／デグレしない」とは現段階では保証できない。特に、日次索引のみの候補選択で、商品本体を都度検索する現行と同じ更新反映を保証することはできない。

### 7条件の達成判定

| 条件 | 今回確認できたこと | 採用に必要な証拠 |
|---|---|---|
| 現在の機能への影響がない | ボット個別設定は画面ロジックを変更せずに実施できる。ジャンル単純置換には表示差がある | TL／BL、形式、作品ID、並び、ページ送り、非公開・復帰、新規作品の反映、購入リンクが現行と一致 |
| 性能劣化が発生しない | フッター停止は先読み効果を失う可能性、compactは解凍等の負荷がある | 同条件で初回・再利用・低速回線・同時利用の画面表示／クリック後遷移の中央値とp95を比較。測定誤差を含めて悪化がないと判断できること。測定不足は合格にしない |
| Read件数が削減する | ボットの高Read画面への巡回が減れば、その分のReadを避けられる。フッター単独にはFirestore削減の大きな効果を期待しない | 同じ画面・条件のRead、および実トラフィックの総Readの減少を確認。空クエリ、索引取得、失敗時の追加Readも含める |
| 課金額が減る | Read以外にも書き込み・索引保存・Web実行・転送・ログの費用があるため、Read減だけでは達成判定できない | 同じ利用量での総費用比較と、反映後の請求集計による実額確認。アクセス量の増減、無料枠・割引、バッチ費用を分離して説明する |
| 大きなデメリットがない | 新たな有料基盤は今回の候補に不要。対象ボット経由の情報利用・流入機会への影響は未測定 | 通常検索・共有プレビュー・DLsite導線を維持し、失う流入と費用削減を比較。未取得の流入指標は「影響ゼロ」と扱わない |
| デグレが発生しない | 既存ソースと架空データの差分は確認済み。新実装の回帰試験はまだない | 関連画面と障害・更新境界の比較を通過。既知の差分・不具合が残る変更は採用しない。試験合格を将来の不具合ゼロの保証とはしない |
| ボットにもある程度対応 | robotsを守る対象への個別抑制は可能。Amazonの公開仕様を再確認した | 生成ルールと適用先、公開ログで対象巡回の減少を確認。指示無視・UA偽装にはこの変更だけでは対処できない |

この条件での実行方針は「既存の3案をすべて通す」ではなく、**機能・性能・総費用の比較を通った変更だけ採用する**。ボット抑制でも節約額と流入への影響の実測は残るため、現時点の判定は実施候補であり、7条件の達成確認済みではない。

### 現行表示を維持する別方式の検討

日次索引のTTLを短くするだけ、または索引で選んだ30商品の本体だけを再取得する方法では、索引作成後に新たに上位へ入った作品・新規作品のIDを発見できない。したがって現在の更新反映を維持する解決にならない。

現行Firestoreクエリの条件・順番・上限を保ち、必要な表示件数が集まるまで候補を段階取得する方法なら、固定されたデータ状態では後続の不要な読み取りを省ける。ただし条件に合う作品が少ない場合は追加通信で遅くなり得る。読み取り中の更新整合性も検討が必要で、現時点では「性能維持まで満たせる方式」とは判定しない。取得項目を減らすだけの変更も、ドキュメントRead件数削減と混同しない。

性能・表示の条件を崩してまで採用せず、まずボット起因の不要なリクエストを減らし、その効果を見て次の変更の必要性を判断する。

## 1. ジャンル詳細

直接の呼び出し元は `web/app/[platform]/[audience]/[category]/genre/[genreId]/page.tsx:60`。取得処理は `web/lib/firebase/products.ts:1054`。ジャンル一覧・検索・新着・セール・作品詳細・サークル詳細は別の取得経路。ただし索引読み込みとフィルター等の共通関数を変更すると、検索・新着・セールにも影響が及ぶ。

### ローカルで再現した表示差

現行ソースから実際の判定関数と `getCatalogProductsPage` を抽出し、Firestoreアクセスを伴わない架空データで5条件を確認した。これは本番での該当件数調査ではない。DB境界は、候補の取得・商品IDでの取得・isActiveによる除外を模擬している。

| 条件 | 現行ジャンル処理 | 既存catalogヘルパーの単純流用 |
|---|---|---|
| `contentType=tl` のみ設定され、contentTypeIds／contentTypesは空 | TLから除外 | TLに含まれる |
| scalarはBL、配列はTL | BLから除外 | BLにも含まれる |
| 販売数上位300件にTLが29件、301件目以降にもTLがある | 29件 | 30件。仕様改善になり得るが同一表示ではない |
| 索引作成後に先頭作品が非公開化。有効作品は残り31件 | 30件を取得可能 | 先に30IDを選ぶと除外後29件。「次へ」が消える |
| 索引作成後、作品の分類がTLからBLに更新 | TLから除外 | 索引のTL判定のまま選び、商品本体のBLをTL画面に出す |

根拠: `productHasContentType` は配列のみ、`candidateHasContentType` はscalarと配列を参照する。`getCatalogProductsPage` は絞り込み→並べ替え→ページ分のID選択→商品取得で、商品本体による分類の再検証がない。ジャンル画面の次ページ判定は `products.length === limitCount`。

診断: `node tmp/audit-genre-compatibility-20260912.cjs`。結果は `tmp/audit-genre-compatibility-20260912.json`。5条件すべてで想定した差分を再現した。変更後のアプリのテスト合格を示すものではない。

### 追加のリスクと実装条件

| リスク | 利用者・他機能への影響 | 必要な条件 |
|---|---|---|
| 索引の更新待ち | 新規・復帰作品が出ない、販売数順や所属ジャンルが古い。カードに表示する最新販売数と順位が食い違う可能性 | 現行の更新反映を維持する。生成時刻の確認だけでは新規IDの不足を発見できず、日次索引だけの方式は今回採用しない |
| 非公開情報の再表示 | 作品・サークル非公開後も索引にIDが残る | 最後に取得した商品本体のisActiveと既存の全可視性判定を必ず適用。IDだけの除外で代用しない |
| 非公開解除の反映遅延 | 非公開中に作った索引にIDがなく、解除後も出ない | 現行より反映を遅らせない。選択済みIDの商品取得だけでは不足IDを発見できない |
| 同じ販売数の順序 | 前後ページで作品が移動する、既存URLの見え方が変わる | 現行Firestoreの販売数降順＋暗黙のドキュメント名降順に合わせる。売上額・評価による二次順序を加えない |
| 販売数の欠損・null等 | 現行orderByで除外される欠損作品を追加する可能性 | compactでは欠損とnull等の情報が失われるため、互換性の扱いを明示して検証。単純なnull→0は避ける |
| 300件等の取得上限撤廃 | 作品数・順位・次ページの有無が変わる | 読み取り最適化と表示対象拡大を分ける。初回は現行上限を再現するか、増える表示を意図した仕様差として確認する |
| 欠落後の補充 | 29件しか出ない、次へが消える。補充だけ追加すると次ページで重複する場合がある | 最終判定・補充・ページ境界を一緒に設計し、重複／欠落を検証。無制限の再取得を避ける |
| 索引破損・欠損・未対応区分 | 空画面、500、旧版の長期表示 | 正常な空索引と利用不可を区別。active版→previous版の検証を維持し、従来のジャンルクエリへ戻せる経路を用意 |
| 障害時のRead増 | compact失敗後、旧search索引全体を読んでから元クエリへ進む可能性 | 共通getConfiguredSearchIndexCandidatesはlegacy索引へ落ちる点に注意。ジャンル用の障害経路を設計し、通常時だけでなく失敗時のReadも測る |
| 共通キャッシュ・判定の変更 | 検索・新着・セールの条件や並びに波及 | グローバルな検索モード・共通判定の意味は変えず、ジャンル専用の互換処理を設ける。共有配列を直接sortしない |
| CPU・メモリ・起動時間 | 同じWebインスタンスの別画面も遅くなる可能性 | 初回の解凍・JSON解析、並列リクエスト、版更新時を測定。既存の容量上限・同時読み込み集約を維持。URLごとに無制限キャッシュを増やさない |
| 少数作品ジャンル・障害時の費用 | 数件で済んだページに索引取得費が追加される | 1作品・多数作品、初回／キャッシュあり、正常／障害を分けてRead・CPU時間を比較 |

**60秒キャッシュは「データが60秒以内に最新になる」という意味ではない。** 現行compactローダーは同じactiveVersionならキャッシュ期限を延長する。日次WorkflowはTL→待機→BL→索引→listViewsの順で、商品更新から索引公開まで時間差がある。手動更新・非公開解除は次回索引まで待つ場合があり、索引更新が止まればさらに古くなる。現在のローダーは主にrowsを返すため、生成時刻による鮮度制御も単なる呼び出し変更では済まない。

前回の本番メタデータは15,746作品・6ブロック。冷えたインスタンスではルート＋版＋ブロックで8ドキュメント、その後に表示商品の取得がある。複数インスタンスでは各々に必要。キャッシュ再利用中に候補選択のReadが減っても、全候補の条件判定・並べ替えはCPUを使う。既存512MiB設定で余裕があるかは新経路の同時実行測定が必要。

価格・画像・アフィリエイトURLは現在の `getProductsByIds` で商品本体を取得して描画すれば維持しやすい。compactの少ない項目だけで商品カードを組み立てる変更は含めない。日々の販売データ集約・年次履歴・書き込み方式には、ジャンル読み取りを局所変更する範囲では直接の変更はない。ただし「画面表示が索引更新に依存する度合い」は増える。

### 実装前に決めること

1. 分類判定、販売数同順位、現行取得上限の扱いを確定する。現行と異なる表示を費用削減の副作用として混ぜない。
2. 現行と同じ商品更新反映を維持する。日次compactだけの方式は採用しない。短時間キャッシュも新たな遅延を生むなら今回の条件を満たさない。
3. 最終商品判定とページ補充・境界を設計する。上限内で安全に表示できない場合の従来経路と、超過Readを決める。
4. ジャンル専用で旧方式へ戻せる切替単位を用意する。共通SEARCH_INDEX_READ_MODEを切り替えて検索・新着・セールまで巻き戻さない。

## 2. ボット個別抑制

変更対象は `web/app/robots.ts`。`*` の現行ルール（`/api/`、`/search` を除外）、sitemap、hostを維持し、対象2エージェントを独立したグループで `Disallow: /` にする想定。

- **設定の取り違えが最大の機能外リスク。** `*` に全拒否を入れると通常検索にも影響する。対象グループに `Allow: /` をコピーすると拒否と競合する。TypeScriptのオブジェクトだけでなく生成された `/robots.txt` を検証する。
- Googlebot、Bingbot、Twitterbot、Facebookの共有プレビュー用エージェント等を一括拒否しない。リンク・OGP情報は残るが、生成ルールの検証と共有プレビュー確認を行う。
- 対象サービスが情報を利用・紹介する機会が減る可能性はある。Amazon公式はAmazonbot／Amzn-SearchBot／Amzn-Userの設定が独立すると説明しており、Amazonbot拒否を「Amazon系の検索もすべて消える」とは評価しない。一方、商業的なデメリットがゼロとも言えない。
- Meta公式資料は取得制限で本文を確認できなかった。細かな用途・例外まで検証済みとは扱わず、反映時に対象トークンと共有用エージェントの分離を再確認する。
- robots.txtは巡回側への指示であり、悪意あるアクセスを強制停止する仕組みではない。UA偽装・指示無視は残り、今回の対応だけで不正アクセス対策が完了するわけではない。
- Amazonは設定反映に約24時間かかり得ると説明している。取り消しも即時には反映されない。ホストごとのrobotsなので、公開されている別ホストがあれば個別に配信・適用を確認する。
- 人がブラウザーで使う機能、外部DLsiteへのクリック、こちらからDLsiteへ行うバッチ取得には、今回のサイト内robots変更による直接の動作変更はない。

前回1時間のUA比率約85%はHTTPリクエスト比率。すべてが削減できるとも、費用85%減とも見込まない。流入影響はリファラー等の取得状況を確認して評価し、取得できない指標は未計測とする。

## 3. フッター先読み停止

変更対象は `web/components/Footer.tsx:55` の内部リンク6件のみ（guide／faq／contact／about／privacy／terms）。現行のブランド・モバイルナビの一部は既にprefetch=false。

- hrefとNext Linkの遷移処理を保てばクリック、キーボード操作、別タブ、戻るの機能は維持できる。DLsite／FANZA／Ci-enの外部リンク、Xリンクは別のa要素である。
- デメリットは、先読み済みだった遷移にクリック後の待ち時間が加わる可能性。特に低速回線・初回起動で確認する。App Routerのprefetch=falseは画面内への出現だけでなくhover先読みも止める。
- 検索向けのa要素・リンク先本文を消す変更ではない。ただし実際のリンクHTMLと遷移を確認する。
- ガイド等の画面はFirestoreを直接読まず、主な効果はSSR処理・転送量の削減。Firestoreの大幅節約とは分けて評価する。
- 前回の6ページ1,083リクエストはすべて `_rsc` だったが、RSC通信には通常遷移も含まれるため、全件が消える保証はない。ボットが実リンクを巡回すればアクセスは残る。
- 先読みはproductionで有効になる機能なので、開発サーバーだけの確認では不足。production buildで、リンクが画面に入る・hover／touchする・実際にクリックする各場面の通信を比較する。

## 受入確認と戻し方

| 対象 | 実装後に必要な確認 | 合格条件／異常時 |
|---|---|---|
| ジャンル条件 | TL／BL／all、全作品形式、特殊文字のgenreId、空ジャンル、30／50／100／200件、1ページ目・途中・末尾 | 承認した仕様差以外の作品ID・順番・件数・次へ判定が一致 |
| 時間差・可視性 | 個別／サークル非公開、復帰、削除、新規追加、分類・販売数変更、索引公開の前後 | 非公開作品を表示しない。現行より反映を遅らせない。補充でページ間重複を作らない |
| 障害 | active破損／previous正常、両方不良、root欠損、正常な空索引、期限切れ、同時読み込み | 想定した旧経路へ復旧。空結果の誤確定や無制限の再試行・大量Readがない |
| 関連画面 | 検索、新着、セール、ジャンル一覧、作品詳細、サークル詳細、外部購入リンク | ジャンル変更を原因とする条件・表示・リンクの差分がない |
| 速度・費用 | 冷えた状態／再利用、少数／多数作品、並列／版切替、障害時 | Read削減を実測。画面の応答性能が現行より悪化せず、メモリの余裕を維持し、CPU等を含む総費用が下がる |
| robots | 生成物とエージェント×パスの適用表、sitemap、公開ホスト、共有プレビュー | 対象2種のみ追加拒否。Google／Bing等の従来ルールを維持 |
| フッター | PC／モバイル、キーボード・別タブ・戻る、production通信 | 先読み通信が減り、実操作で6ページすべて表示できる |

追加条件を受けて、以前の「フッター→robots→ジャンル」という順序を修正する。**robotsの個別設定を最初の検証候補とし、フッターは性能比較まで保留、ジャンルは現行の更新反映も維持できる別設計まで保留する。** 各変更は影響範囲ごとに分け、条件未達の変更は反映しない。同時にすべて変更すると、表示不具合・速度変化・費用変化の原因が判別しにくい。

デプロイ後は48〜72時間を初期評価期間とし、日次バッチ時間を分けてFirestore Read、画面リクエスト、5xx、p95、CPU／メモリを比較する。アクセス量と正常系／障害系を考慮し、ボット比率だけから削減額を計算しない。検索流入・紹介流入・DLsiteクリックはより長い期間で確認する。新たな診断ログは件数を制限し、それ自体の費用を増やさない。

非公開表示・分類混入・ページ欠落・5xx／遅延の増加が発生したら、該当変更を個別に戻す。ジャンル専用切替か該当コードのロールバックを使う。フッターはprefetch設定、robotsは対象グループを戻す。デプロイや巡回側の設定再取得には時間が必要で、即時反映を保証しない。
