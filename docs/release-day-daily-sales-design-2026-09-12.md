# 発売初日の日別販売本数を翌日の累計で確定する設計案

作成日: 2026-09-12。現行ソースを確認した設計資料。アプリ実装、本番設定変更、本番データ補完、新仕様のテスト実行は未実施。

最新の前提: ユーザー指定により、通常日の再実行は今回の設計・修正対象から外す。前回の[統合レビュー](four-change-integrity-review-2026-09-12.md)で確認した再実行時の挙動は、今回の反映を止める条件にしない。発売初日の確定だけを追加し、以降の通常日次計算と既存の同日判定は維持する。

## 1. 採用する仕様

発売日をDとする。通常の日次収集で、D+1に実際に取得できた累計販売本数を、Dの`dailySalesCount`へ代入する。発売当日に取得した累計は差し引かない。D+2以降は既存の前回累計との差分計算を維持する。

| 実際の取得日 | 取得した累計 | 履歴の日付 | dailySalesCount | 次の差分計算に使う累計 |
|---|---:|---|---:|---:|
| 9/1（発売日） | 50 | 9/1 | 未算出のまま | 50 |
| 9/2 | 120 | 9/1 | **120** | **120** |
| 9/3 | 200 | 9/2 | **80** | 200 |
| 9/4 | 260 | 9/3 | **60** | 260 |

- 「翌日のバッチ実行時」は、各作品の実際の取得時点と定義する。バッチ全体の終了時刻までの本数は、再取得なしでは分からない。
- 発売初日は発売から翌日の取得時点までを含む。この値を厳密な暦日の24時間売上や実際の入金額とは表示しない。
- 対象は同じ作品・同じ販売本数の定義の`product.salesCount`。`totalSalesCount`や別エディションの本数へ切り替えない。
- 発売当日の取得に失敗し、翌日に初登録できた場合も、発売日が確実なら同じ仕様で確定する。

## 2. 現行実装から分かった影響

| 経路 | 現行の処理 | 設計で必要な対応 |
|---|---|---|
| 日次収集 | `fetchDailyPriorityProducts.ts:272`で保存日を前日と発売日の遅い方にする。`:371`で初回は未算出、`:384`で同じ保存日の再実行は差分を維持する | 発売翌日の初日確定を、初回・同日再実行の一般処理より前に判定する |
| ランキング | `rankingMetrics.ts:201`が日別本数を受け取り、`:212`が単価を掛ける | 初日120本を同時に渡し、日次順位・日次推定売上を更新する |
| ジャンル日次集計 | `rebuildGenreIndex.ts:151`がランキング用の日別本数を使う | 初日分が加わることは仕様変更として検証する |
| 履歴からのグラフ | `web/lib/firebase/products.ts:1332`が日別本数を読む | 初日120本を表示する。サークルの履歴集計も同様 |
| 初期表示用グラフ | 同ファイル`:1247`は累計スナップショットの差分、`:1261`は最新日だけランキング値で補う | 履歴だけを修正すると、翌日以降に初日の点が消える。確定した初日を別途保持して同じ値を表示する |
| 年次保存 | `productMetricHistory.ts:32`は保存項目を限定する | 新しい計算根拠の項目を追加するなら、型だけでなく年次変換・比較・移行ツールも対応する |
| 過去作品収集 | `fetchGirlsReleaseOldProducts.ts:507`は日次収集とは別の基準日で差分を作り、過去履歴にも書く | 初日確定値・次回比較用の累計を上書きしない保護が必要 |
| 保存バッファ | `fetchDailyPriorityProducts.ts:466`は1書き込み単位でコミット境界を判定する | 同じ作品の本体と履歴が別コミットに分かれないよう、作品単位で空きを確保する |

日次順位や日次推定売上、グラフの値は初日分を含むように変わる。「影響なし」は全ての表示数値を固定する意味ではなく、この意図した補正以外の計算規則・機能を維持する意味で評価する。

## 3. 取得漏れを防ぐ対象選定

現行の候補統合は当日発売・人気順・作品形式別人気順・累計販売本数順（`fetchDailyPriorityProducts.ts:979-1022`）。前日発売の全登録作品を翌日再取得する保証はない。

- 登録済みの前日発売作品を日次候補に追加する。作品の日付と既存の収集・公開制御を確認し、全商品走査は行わない。
- 発売日範囲を絞った取得とページ送りで候補を列挙し、既存の対象と作品IDで重複排除する。取得済みの商品データは既存商品読み取りに再利用する。
- 人気リストの件数上限でこの対象を落とさない。TL/BLの重複、同一作品の複数経路も従来の識別規則で整理する。
- 前日発売でも公開・収集停止等の既存方針で対象外となる作品は、処理対象と混同せず集計する。
- 翌日の取得が失敗したら、その日付内で既存の再試行を行う。翌々日以降の現在累計を初日分として埋めない。

この対象追加には、候補検索のReadと、従来対象外だった作品の外部取得・DB更新が発生し得る。計算分岐だけの場合と区別して件数・時間・費用を見積もる。

## 4. 初日確定の判定と保存

`buildDailySalesPatch`へ論理バッチ日と実際の取得時刻を渡す。前日保存日だけでは、発売当日と翌日を区別できない。事前取得済みの商品も、取得時刻を持ち回り、保存時刻で代用しない。

確定条件は全て満たすこと:

1. 正規化・実在日チェック済みの発売日Dを取得できる。
2. 保存先日付がD、バッチ日がD+1、実際の取得日もJSTでD+1である。
3. 販売本数が有効な非負整数である。0本も確定値として扱う。
4. 同じ作品・販売本数の定義である。既存情報と発売日が食い違う場合は、自動で初日確定しない。
5. 後日の比較基準が既に存在するなど、古い処理が新しい状態を巻き戻す状況ではない。

条件成立時は、通常の「前回データなし」「同じ保存日」の分岐より先に処理する。

- `dailySalesCount = 今回累計`、`dailySalesStatus = calculated`を保存する。既存利用側が認識しない新しいstatus値は増やさない。
- 次回比較用の`lastDailySalesSnapshotDate/Count`と、その日の`rankingMetrics`も同じ今回累計・日別値に合わせる。架空の0本スナップショットを履歴や`recentSalesSnapshots`へ追加しない。
- 計算根拠は追加の任意項目`dailySalesBasis = release_day_cumulative`で識別する案とする。取得時刻・発売日・確定時刻を追跡できるようにする。差分の基準日・期間へ架空の取得情報を埋めない。
- 初日履歴に既に差分用の証跡がある場合、上書き対象の古い根拠・`periodSalesCount`を明示的に整理する。mergeで古い値を残さない。
- 商品本体に小さな任意項目`releaseDaySales`（日付、本数、採用単価、取得時刻、定義バージョン）を同じ書き込みで保存する。これは初期グラフ用で、累計へ加算する値ではない。

発売日と翌日のバッチは、保存先が同じ発売日でも、別日に行う正常処理である。通常日の再実行を対象外としても、この初日確定の特例は必要。初日確定時に履歴・比較基準・スナップショット・ランキング・初日表示用情報を同じ累計へ揃えることで、翌日以降は既存の差分計算をそのまま使える。

通常日再実行のための差分再計算、元の基準を固定する追加状態、旧データからの基準復元Read、通常日再実行時の新仕様テストは追加しない。初日値は加算ではなく代入で保存し、同じ保存内容の再送でも二重加算しない。

## 5. 障害・別経路への保護

- 一度確定した初日を、後続の取得失敗・欠損値で`null`へ戻さない。有効な累計が減少した等の異常も自動採用せず、前回確定値と比較基準を保って要確認にする。
- 同一作品の本体・対象履歴を一組でコミットする。`dual`時は旧日次・年次も同じ組に含め、バッファ境界で分離しない。
- 通常日再実行の対策だけを目的とした共有収集ロックや実行世代の新設は、この初日修正の必須作業から外す。ジャンル集約の公開競合を防ぐ更新番号の確認は別目的として維持する。
- `fetchGirlsReleaseOldProducts`等が別方式で後から履歴へ書き込む経路は確認し、初日確定値・比較基準を壊さない保護を入れる。過去補完は日次処理と同時に走らせない。
- 誤った`BATCH_DATE`や翌々日まで遅れた取得は、発売翌日の取得値として採用しない。
- バッチ内で失敗した作品だけの既存再試行（`retryFailedTargets`）は維持する。正常取得済みの通常日データを取り直すための機能へ変更しない。
- 上記の保護が全ての有効な本番書き込み経路に反映される前には、新仕様を有効にしない。

## 6. 表示・集計の整合

- `releaseDaySales`から、初期表示用グラフの該当日を1点だけ補う。日付をキーに既存の点と統合し、最新ランキング値や履歴取得結果と二重加算しない。
- 初期表示、期間拡大後の履歴API、サークルの合算グラフで同じ値・同じ単価を使用する。翌日以降や35日分のスナップショット境界でも確認する。
- 表示対象外の作品を追加しない。初日補完のために各画面で個別の追加履歴Readを発生させない。
- 日次ランキング・ジャンル日次集計は初日分を反映して既存の後段処理で再構築する。累計・週間・月間は同一の入力スナップショットなら現行と一致することを確認する。
- 前日発売の追加取得により、従来より新しい累計を得た作品の週間・月間・累計値が更新される場合は、計算式の変更とは区別する。
- `metricYears`と`dailyMetrics`には同一の計算結果を書き込む。年次変換、読み出し、比較、移行スクリプトの保存項目・型を一致させる。
- 公開前にグラフの実際の注記を確認する。暦日の24時間集計と誤認させる場合は、「翌日の取得時点までを含む」ことを必要な箇所に明記する。

## 7. 過去分の補完と反映順

過去分の補完は日次バッチから分離する。先にdry-runで対象・採用値・除外理由・予定Read/Writeを一覧化する。

- 発売日の履歴があり、そこに保存された累計と実際の取得時刻が「発売翌日取得の値」だと確認できる場合だけ補完する。
- 年次ドキュメント全体の`updatedAt`は、その点の取得日を証明しない。点固有の取得時刻等の証拠が必要。
- 翌日取得がない、後日の手動取得で値が変わっている、発売日が不明・変更された等は自動補完しない。現在の累計からの逆算も行わない。
- 補完は初日履歴と`releaseDaySales`を更新する。現在の`lastDailySalesSnapshot*`、最新日の日次ランキング、最近の比較基準を過去へ戻さない。派生表示を再生成する場合も現在の基準日を保つ。
- 現在値が読み取り時点から変更されたら上書きしないよう、補完対象に更新前条件を設ける。日次処理と同時に走らせない。
- 変更前の値・変更したフィールドを保存し、データを戻す場合は後続の正常更新を消さない条件付き復旧にする。機能フラグをOFFにするだけでは既に補完したデータは戻らない。

反映順は、表示互換対応・全書き込み経路の保護 → 初日確定の有効化 → 翌日と翌々日の結果確認 → 根拠がある過去分の補完 → 履歴全件照合 → 二重書き込み終了とする。日付仕様の変更と保存形式の切替を同時に有効化しない。

## 8. 検証・採用条件

以下は実装後に行う試験であり、本資料作成時点では未実施。

| ケース | 合格条件 |
|---|---|
| 基本の50→120→200→260 | 初日120、翌日80、その翌日60。累計へ重複加算なし |
| 発売当日失敗、翌日初登録 | 発売日が確実なら初日120を保存 |
| 発売日と翌日が同じ履歴日へ保存 | 発売翌日の120本を初日として確定し、翌日以降は既存の差分へ進む |
| 同じ初日保存内容の再送 | 代入保存で二重加算せず、商品と履歴が一致する |
| 0本・欠損・減少・取得失敗 | 0を未算出と誤認せず、失敗で確定値を消さない |
| 翌日未取得・翌々日取得 | 2日以上の累計を初日に押し込まない。未確定を記録 |
| 月末・年末・うるう日 | 発売日と翌日の判定、保存年を正しく扱う |
| 論理日付と実取得日の不一致 | 誤った過去日の確定を行わない |
| 失敗作品の再試行・途中停止・コミット境界 | 同じ作品の本体・旧日次・年次が食い違わない。成功作品の通常日再実行対応は含めない |
| 過去作品取得・補正との順序違い | 初日確定と後日比較基準を壊さない |
| 初期グラフ・履歴API・サークル合算 | 初日が後日消えず、二重計上しない |
| 日次順位・ジャンル日次 | 初日分を含めて一致。非公開・分類・表示条件を維持 |
| 週間・月間・累計・価格・リンク等 | 同じ入力なら本修正前と一致。意図した数値補正以外の変更なし |
| legacy/year/dual・過去補完 | 数値・状態・計算根拠が一致。最新状態を巻き戻さない |
| 性能・費用 | 画面の追加Readを発生させず、候補追加・保存データ増分を含め実測する |

計算・商品内の初日情報・履歴を既存の書き込みへまとめるため、計算自体で作品ごとの追加ドキュメント読み書きは不要な設計にできる。通常日再実行のための追加状態・基準復元Read・収集ロックは増やさない。ただし候補追加、初回補完、少量の保存・転送増分は別に発生し得る。費用やバッチ時間が全く増えないとは、実測前に判定しない。
